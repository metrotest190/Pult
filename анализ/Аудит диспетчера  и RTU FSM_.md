# Аудит диспетчера `mb.c` и RTU FSM `mbrtu.c`

**Граница проверки:** только `mb.c`, `mbrtu.c`, `mbcrc.c` и согласованность с приложенным портом. Исправления функций FC01–23 и порта не переоцениваются. Все ссылки ниже относятся только к приложенному исходному коду в формате `file:line`.

> **Вывод:** `EV_ERROR` в данном дереве исходников отсутствует и `mbrtu.c` его не публикует, поэтому отсутствие `case EV_ERROR` не является дефектом. Зафиксированы пять независимых проблем: одна связана с максимальным RTU-кадром, одна — с совместимостью FIFO(8) и единственного буфера кадра, две — с жизненным циклом/переопределением обработчиков, и одна — с отказом UART TX.

## Подтверждено корректным

| Пункт ТЗ | Статус | Проверка по коду |
|---|---|---|
| **EV_ERROR** | **Не существует; дефекта нет** | `eMBEventType` содержит только `EV_READY`, `EV_FRAME_RECEIVED`, `EV_EXECUTE`, `EV_FRAME_SENT` (`mbport.h:39–45`). `mbrtu.c` публикует только `EV_FRAME_SENT` (`mbrtu.c:308`), `EV_READY` (`mbrtu.c:329`) и `EV_FRAME_RECEIVED` (`mbrtu.c:335`). В `STATE_RX_ERROR` он намеренно не публикует событие и после T3.5 возвращается в idle (`mbrtu.c:338–349`). Поэтому `eMBPoll()` не обязан содержать несуществующий `case EV_ERROR`. |
| **FIFO и порядок событий** | **Порядок FIFO корректен, payload-ограничение — MBRTU-02** | Posting добавляет в tail, get снимает из head под критической секцией (`portevent.c:40–75`). `EV_FRAME_RECEIVED` обрабатывается до постановки `EV_EXECUTE` (`mb.c:358–366`); TX завершение ставит `EV_FRAME_SENT` (`mbrtu.c:306–313`). Глубина 8 сохраняет порядок событий, но сама по себе не делает `ucRTUBuf` многокадровым. |
| **Broadcast FC06/FC16** | **Корректно для существующей карты** | `EV_EXECUTE` запускает handler независимо от slave/broadcast адреса (`mb.c:370–384`), а отправка ответа обёрнута условием `ucRcvAddress != MB_ADDRESS_BROADCAST` (`mb.c:387–403`). Поэтому broadcast-записи применяются и ответа не получают. Broadcast-чтение также выполнит чистый read callback без ответа; оно не меняет карту регистров, но master не должен использовать такую операцию. |
| **Окно RX/TX на 4-проводной линии** | **Корректно по Modbus slave модели** | Передача включает `vMBPortSerialEnable(FALSE, TRUE)` (`mbrtu.c:210–213`), что отменяет RX и запускает TX (`portserial.c:230–240`). После фактического завершения последнего байта FSM публикует `EV_FRAME_SENT` и немедленно вызывает `vMBPortSerialEnable(TRUE, FALSE)` (`mbrtu.c:306–312`). RX выключен только во время собственного ответа. На 4‑проводной физике это не требует DE; мастер не должен посылать следующий запрос до завершения ответа. |
| **Минимальный и переполненный RTU-кадр** | **Корректно, кроме максимальной границы MBRTU-01** | Минимальная длина определена как 4 байта (`mbrtu.c:46–50`), что соответствует address + function + CRC16. CRC проверяется по всему принятому кадру (`mbrtu.c:157–176`). При 257-м байте FSM переходит в `STATE_RX_ERROR` без записи за границу (`mbrtu.c:267–276`), затем T3.5 не публикует кадр и возвращает idle (`mbrtu.c:338–349`). |
| **T3.5 при 115200** | **Корректно; 1750 мкс — не баг** | Для `ulBaudRate > 19200` задаётся 35 тиков (`mbrtu.c:95–114`). Порт начинает с `CNT=0` и `timerCounter=0` (`porttimer.c:48–58`), вызывает RTU callback при равенстве счётчика периоду (`porttimer.c:95–102`). При 50 мкс это **35 × 50 = 1750 мкс**. Комментарий `1800us` в `mbrtu.c:100` неточен, но код верен. |
| **T3.5 при 9600** | **Корректно с квантованием таймера** | Формула `(7 × 220000) / (2 × baud)` в `mbrtu.c:104–112` даёт `80.208…` тика для 9600 и после целочисленного усечения — 80 тиков, то есть 4000 мкс. Идеальные 3.5 символа при 11 битах составляют около 4010 мкс; ошибка меньше одного периода таймера 50 мкс. |
| **eMBInit** | **Корректно** | Адрес broadcast/вне 1…247 отклоняется (`mb.c:133–138`). Для RTU инициализируются функции/колбэки и передаётся результат `eMBRTUInit()` (`mb.c:145–157`), затем создаётся event port (`mb.c:177–188`). Игнорирование `ucPort` портом явно допустимо: `portserial.c:243–260` его подавляет и проверяет реальную CubeMX-конфигурацию USART1. |
| **eMBEnable/eMBDisable и EV_READY** | **Первичный цикл корректен; повторный — MB-03** | Enable запускает RTU (`mb.c:291–305`); RTU устанавливает `STATE_RX_INIT`, включает RX и T3.5 (`mbrtu.c:125–137`); истечение ставит `EV_READY`, который `eMBPoll()` корректно снимает как no-op (`mbrtu.c:327–330`, `mb.c:351–356`). Stop отключает RX и timer (`mbrtu.c:140–146`). |
| **Таблица обработчиков** | **Ёмкость корректна; override — MB-04** | Включено 10 built-in функций (`mbconfig.h:97–125`), массив рассчитан на 16 (`mbconfig.h:78–85`), инициализатор `mb.c:94–125` содержит ровно 10 условных entries. Поиск исполнителя идёт от начала массива (`mb.c:370–384`), что создаёт только описанную проблему override. |
| **CRC16 и wire order** | **Корректно** | `usMBCRC16()` начинает с `0xFFFF` и использует таблицы `mbcrc.c:83–96`; прием считает CRC со включёнными двумя CRC-байтами и ожидает ноль (`mbrtu.c:157–160`); отправка добавляет low byte, затем high byte (`mbrtu.c:205–208`). |
| **`xNeedPoll` из ISR** | **Не-дефект** | Значение возвращается RTU FSM (`mbrtu.c:283–317, 321–351`), но callback-контракт связывает его с пробуждением заблокированной задачи (`mbport.h:96–112`). В текущем bare-metal порте задача не блокируется и FIFO опрашивается главным циклом; игнорирование значения IRQ-обёртками осознанно. |

## Готовые точечные исправления

### MBRTU-01: граница максимального кадра

В `mbrtu.c`:

```c
ENTER_CRITICAL_SECTION();
assert( usRcvBufferPos <= MB_SER_PDU_SIZE_MAX );
```

### MB-03: очищать FIFO на новом enable-сеансе

Замените успешную ветку `eMBEnable()` в `mb.c`:

```c
if( eMBState == STATE_DISABLED )
{
    /* The stack is inactive here; discard events from a previous session. */
    if( xMBPortEventInit() != TRUE )
    {
        eStatus = MB_EPORTERR;
    }
    else
    {
        pvMBFrameStartCur();
        eMBState = STATE_ENABLED;
    }
}
else
{
    eStatus = MB_EILLSTATE;
}
```

### MB-04: корректно заменять зарегистрированный handler

В `eMBRegisterCB()` замените условие выбора ячейки:

```c
if( ( xFuncHandlers[i].ucFunctionCode == ucFunctionCode ) ||
    ( xFuncHandlers[i].pxHandler == NULL ) )
{
    xFuncHandlers[i].ucFunctionCode = ucFunctionCode;
    xFuncHandlers[i].pxHandler = pxHandler;
    break;
}
```

### MBRTU-05: не терять байт при отказе запуска UART TX

В ветке `usSndBufferCount != 0` функции `xMBRTUTransmitFSM()`:

```c
if( xMBPortSerialPutByte( ( CHAR )*pucSndBufferCur ) == TRUE )
{
    pucSndBufferCur++;
    usSndBufferCount--;
}
else
{
    /* The byte was not accepted; do not consume it without a TX callback. */
    usSndBufferCount = 0;
    eSndState = STATE_TX_IDLE;
    vMBPortSerialEnable( TRUE, FALSE );
    /* Increment a project diagnostic counter here. */
}
```

### MBRTU-02: требуется архитектурное решение

Не рекомендуется «лечить» MBRTU-02 перестановкой event codes или вызовом `eMBPoll()` из ISR. Безопасный вариант — очередь frame descriptors с собственным payload (например, два или восемь PDU буферов в зависимости от допустимой RAM) и передача в `EV_EXECUTE` индекса descriptor. Альтернатива — намеренно останавливать RX после T3.5 до окончания `EV_EXECUTE` и отдельно включать RX после broadcast; она снижает пропускную способность и требует новой точки синхронизации между `mb.c` и `mbrtu.c`.

## Ограничения проверки

Полная ARM-сборка и аппаратный тест не выполнялись: не приложены полное дерево STM32 HAL/CMSIS, startup-файл, актуальные `main.c`/`stm32f1xx_it.c`, `.ioc`, `.map` и журнал сборки. Выводы по `mb.c`/`mbrtu.c` и приложенному port-контексту являются статическими.
