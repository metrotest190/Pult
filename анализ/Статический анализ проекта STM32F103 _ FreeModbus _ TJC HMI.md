# Статический анализ проекта STM32F103 / FreeModbus / TJC HMI

**Объект проверки:** предоставленные файлы прикладного кода, порта FreeModbus, заголовков, обработчиков IRQ и конфигурации CubeMX/CubeIDE.  
**Платформа:** STM32F103C8Tx, STM32 HAL, FreeModbus RTU, USART1 (Modbus), USART3 (TJC).  
**Метод:** ручной статический анализ потоков данных, взаимодействия с ISR и интерфейсов HAL/FreeModbus. Полная сборка не выполнялась: в снимке отсутствуют полный исходный каталог HAL/CMSIS, модули ядра FreeModbus и ARM-кросс-компилятор. Это не влияет на выводы, помеченные как **подтверждённые**: они следуют непосредственно из предоставленного кода.

> **Итог:** обнаружен один безусловный дефект, препятствующий компиляции, и несколько серьёзных ошибок конкурентного доступа к UART TJC. До испытаний на оборудовании необходимо в первую очередь исправить заголовок TJC, убрать принудительное изменение состояния HAL UART и разделить обработку ответов `addt` от пользовательских команд экрана.

## Критические ошибки обмена с TJC

| ID | Место | Дефект | Сценарий отказа | Рекомендация |
|---|---|---|---|---|
| **C-01** | `portserial.c:105–129` | `tjc_flush_tx()` ждёт максимум 100 мс, но затем **всё равно** переключает буфер и запускает новую передачу. При ошибке он вручную устанавливает `TJC_UART.gState = HAL_UART_STATE_READY`. | Если предыдущая передача ещё идёт, новый запуск возвращает ошибку/`HAL_BUSY`. Флаг `tjc_tx_busy` ложно очищается, а изменение `gState` рассинхронизирует внутреннее состояние HAL с периферией. Следующая передача может перезаписать контекст активного TX или перемешать команды экрана. | Не запускать новую передачу, пока `tjc_tx_busy != 0`; не менять поля HAL вручную; обрабатывать и возвращать статус API. |
| **C-02** | `main.c:323–338, 369–390` | Один RX ring buffer одновременно используется для `0xFE`/`0xFD` ответа `addt` и команд `0x55 0xAA ch state`. В состояниях ожидания код удаляет каждый байт, отличный от требуемого статуса. | Команда видимости, пришедшая во время `addt`, уничтожается побайтно: первым удаляется `0x55`, затем `0xAA`, канал и состояние. Комментарий о «сохранении команд» не соответствует фактическому коду. | Декодировать входящий поток в **одном** месте и разнести результаты: флаги ответов `addt` и отдельная очередь команд видимости. Не удалять нераспознанные байты вторым потребителем. |
| **C-03** | `portserial.c:85–96` | При заполненном `tjc_tx_buf` функция ждёт 10 мс, после чего просто отбрасывает байт без статуса и счётчика ошибки. | Теряются в том числе байты `0xFF 0xFF 0xFF`, завершающие TJC-команду. Экран получает обрезанную команду, а синхронизация протокола становится непредсказуемой. | Сделать функцию возвращающей `bool`/статус, не терять фреймы частично: либо резервировать место до формирования всей команды, либо ставить в очередь целую команду. |

Неблокирующий UART API сообщает только о старте операции, а завершение должно обрабатываться callback-функцией; этот контракт нарушается, когда приложение самостоятельно сбрасывает состояние драйвера.[1] В проекте callback `HAL_UART_TxCpltCallback` уже существует и должен быть единственным источником установки `tjc_tx_busy = 0` (`portserial.c:262–268`).

### Безопасная схема передачи TJC

Вместо ожидания в `tjc_flush_tx()` нужна политика очереди. Перед формированием команды следует проверить свободное место для **всей** команды. При занятости UART оставить данные в очереди и вернуться в главный цикл. Буфер переключать только после успешного запуска `HAL_UART_Transmit_IT()`.

```c
/* Идея интерфейса: не изменять gState и не делать busy-wait. */
bool tjc_try_flush(void)
{
    if (tjc_tx_busy || tjc_tx_len == 0U) {
        return false;
    }

    uint8_t *const send_buf = tjc_active_buf;
    const uint16_t send_len = tjc_tx_len;

    if (HAL_UART_Transmit_IT(&TJC_UART, send_buf, send_len) != HAL_OK) {
        tjc_tx_error_count++;
        return false;                 /* буфер и длина остаются для повторной попытки */
    }

    tjc_active_buf = (send_buf == tjc_tx_buf_a) ? tjc_tx_buf_b : tjc_tx_buf_a;
    tjc_tx_len = 0U;
    tjc_tx_busy = 1U;
    return true;
}
```

В реальном исправлении переключение указателя, длины и флага нужно защитить короткой критической секцией, потому что флаг завершения меняется в IRQ.

| ID | Место | Дефект | Последствие | Исправление |
|---|---|---|---|---|
| **H-01** | `portevent.c:29–68` | Очередь состоит из одного слота; `eQueuedEvent` и `xEventInQueue` не `volatile` и не защищены критической секцией. При новом событии старое безусловно перезаписывается. | Потеря событий `EV_FRAME_RECEIVED`, `EV_EXECUTE` или `EV_FRAME_SENT`; при оптимизации компилятора возможны некорректные чтения переменной-флага между ISR и `eMBPoll()`. | Защитить чтение/запись сохранением `PRIMASK`; сначала записывать событие, затем флаг. | **H-02** | `mt_port.c:19, 29–46` | `ExitCriticalSection()` безусловно декрементирует `lockCounter`; при дисбалансе счётчик переполняется. `__enable_irq()` не восстанавливает исходный `PRIMASK`. | Возможна вечная блокировка IRQ или, наоборот, включение IRQ, которые были отключены внешним контекстом/вызывающей функцией. | Запоминать исходный `PRIMASK` при первом входе; на последнем выходе восстанавливать его через `__set_PRIMASK(saved_primask)`. Изменение скорости в `eMBInit()` создаст ложное ощущение применённой конфигурации. | Проверять `modbusUart != NULL`, сверять конфигурацию CubeMX с аргументами, возвращать `FALSE` при ошибке запуска TX/RX. |

Повторный вызов может вернуть `HAL_BUSY`, а его статус игнорируется; ISR создаёт лишнюю нагрузку и скрывает ошибки. | Выбрать одну модель: **circular** без перезапуска в TC (предпочтительно для выборки GPIO) либо normal mode с перезапуском только после успешного завершения. |

Для интерфейса порта проще оставить обычные `void`-функции. |

Таймер TIM3 действительно запускается с периодом 50 мкс (`Prescaler=71`, `Period=49` при частоте таймера 72 МГц), поэтому программный счётчик соответствует единицам, ожидаемым `xMBPortTimersInit()` (`porttimer.c:50–63`, `.ioc:221–248`). Проблема находится не в номинальной частоте, а в надёжности запуска/синхронизации и в определении функции как внешней `inline`.

### Рекомендуемая реализация критической секции

```c
static volatile uint32_t lock_counter;
static uint32_t saved_primask;

void EnterCriticalSection(void)
{
    const uint32_t primask = __get_PRIMASK();
    __disable_irq();
    if (lock_counter++ == 0U) {
        saved_primask = primask;
    }
}

void ExitCriticalSection(void)
{
    if (lock_counter == 0U) {
        Error_Handler();              /* или assert в отладочной сборке */
    }
    if (--lock_counter == 0U) {
        __set_PRIMASK(saved_primask);
    }
}
```

Эта схема применима, если данные функции используются только в обычном контексте и не вызываются из NMI/HardFault. Для ISR и основного цикла предпочтительнее короткие специализированные операции с сохранением/восстановлением `PRIMASK`, а не длительное удержание глобальной блокировки.

## Минимальный регрессионный набор

1. Выполнить чистую сборку Debug и Release с включёнными предупреждениями `-Wall -Wextra -Werror=implicit-function-declaration`.
2. Подать на USART3 непрерывную смесь команд `0x55 AA ch state` и ответов `0xFE/0xFD` во время перерисовки всех трёх графиков; проверить, что изменение видимости не пропадает.
3. Замедлить или отключить TX TJC на время более 100 мс. Убедиться, что приложение не меняет поля `UART_HandleTypeDef` вручную и не искажает последующие команды.
4. Нагрузить Modbus RTU последовательностью запросов `03`, `04`, `06`, `10`, а также заведомо неподдерживаемых `01/02/05/0F`; ожидаемые исключения должны соответствовать документированной карте регистров.
5. Записать в float-регистры нормальные числа, крайние значения, NaN и Inf. Экран не должен зависать или передавать недопустимые значения в `int`.
6. Удерживать обе кнопки Jog, затем отпускать их в разном порядке; выдаваемая команда должна определяться согласованной спецификацией приоритета.
7. Проверить DMA GPIO осциллографом/логическим анализатором: обновление `input_buffer_A/B` — 1 кГц без остановки и без ошибок DMA.

## Граница достоверности

В отчёте **не** делается вывод о физическом управлении направлением RS-485: в предоставленных файлах нет информации о трансивере и выводе DE/RE. Также не проверялись точные соглашения адресации мастера Modbus (например, 0-based/1-based представление `0x1000`, `0x2000`, `0x4000`), поскольку отсутствуют исходники функций FreeModbus, формирующих `usAddress`, и спецификация карты регистров мастера. Это следует отдельно подтвердить интеграционным тестом.
